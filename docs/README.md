# 今天该吃什么 —— 一个完整的「决策模型」教学项目

用一份**自动生成的数据集**，训练一个**两层决策模型**，回答「在什么情况下该吃什么」。

这个项目是按你的场景定制的：**单步决策 + 结果导向信号 + 小动作空间**。
它同时也是上一轮讨论里那套方法论的完整可运行实例 —— 数据怎么造、信号怎么定、
模型怎么搭、怎么评估一个决策模型（而不是一个分类模型）。

## 3. 数据集长什么样

### 3.1 菜品库 `artifacts/dishes.csv`（824 道菜 / 19 个品类）

每道菜带**客观属性**，而不是只有一个名字：

```
dish_id, dish_name, category, time_cost, price, spicy, heavy, healthy,
temperature, carb, protein, taboo, [region, is_veg, meal_slots, frequency]
```

- `heavy` 厚重感 1-5（1=清爽，5=很顶）
- `healthy` 健康度 1-5
- `temperature` 0=凉 / 1=温 / 2=热
- `taboo` 过敏原标签（海鲜/乳制品/麸质/花生），多值用逗号分隔
- `is_veg` 纯素标记（**刻意与 `taboo` 分开**：素食是饮食约束、不是过敏原）
- `region` / `meal_slots` / `frequency` 是后加的参考列，不参与特征编码

19 个品类：川菜、东北菜、湘菜、本帮江浙菜、长三角粉面、广府家常菜、家常炒菜、
早餐粥点、老火汤羹、烧烤小吃、煲仔饭碟头饭、糖水甜品、西式简餐、火锅麻辣烫、
早茶点心、广式粥粉面、烧腊卤味、轻食健康、面包甜点

菜品库的来源与生成脚本在 `dish-library/`：

| 脚本 | 作用 |
|---|---|
| `_gen_dishes_lr.py` | 长三角/珠三角基础库（448 道，含宴席与长尾） |
| `_gen_dishes_cn3.py` | 本次新增：**湘菜 95 + 东北菜 125 + 川菜 140 = 360 道** |
| `merge_final.py` | 与模型原有的 47 道合并、去重、归一，产出 `app/artifacts/dishes.csv` |

合并口径：菜名去重且**旧库优先**（保留其手工调过的属性）；旧库的同菜异名
（`西红柿炒蛋+米饭` → `番茄炒蛋` 等 9 处）已归一；旧库两个窄品类
（`中式快餐盖饭` 6 道、`面食粉面` 6 道）并入同类大品类
（`煲仔饭碟头饭` / `长三角粉面`），否则这两个品类候选太少、
第二层的品类内排序学不动。

> **注意**：`category` 覆盖必须完整。`SLOT_CAT_BONUS` 若漏配某个品类，
> 该品类在「时段适配度」上恒得 0 分、会在时段竞争里系统性吃亏（属于静默出错），
> 所以 `build_dataset.py` 导入时就断言全部品类都有配置。

### 3.2 情境 + 结果信号 `artifacts/samples.csv`（7340 行）

一行 = 一次观测：

| 字段 | 含义 |
|---|---|
| `time_slot, hunger, available_time, budget, mood, weather, companion, health_goal, spicy_tol, taboo` | **情境**（状态） |
| `dish_name, category` | **观测到的是哪道菜**（动作） |
| `source` | `chosen`=实际选了这道菜 / `considered`=考虑过并顺手打了分 |
| `utility` | 这道菜在当时那个情境下的**真实效用**（0~1） |
| `observed_signal` | **训练用的结果信号** = 真实效用 + 感知噪声 |
| `split`, `shift` | 划分标记 |

- `chosen` 行 4224 条（每个情境 3 条）× **排序损失**：学"该选哪个"
- `considered` 行 956 条（35% 的情境附带同品类前 3 名评分）× **回归损失**：学"有多好"

另有 `artifacts/scenario_utility.npy`（2000×317）：**每个情境下所有菜的真实效用矩阵**。
第二层的排序目标必须逐菜不同，唯一正确的来源就是这个矩阵（见 §5 的坑 4）。

这个区分很重要：**只有 `chosen` 能当排序目标**（被选中的才是"结果"），
`considered` 只提供数值监督。

### 3.3 关键设计（这些决定了项目成败）

1. **效用函数是可解释的常识规则**，不是随机数。例如：
   - 早餐时段选火锅 → 重罚；夜宵选沙拉 → 重罚
   - 心情低落 → 偏好辣和重口（安慰性食物）
   - 雪天 → 偏好快 + 热乎（不想出门）
   - 有朋友一起 → 偏好可以慢慢吃的大菜
   - **健康诉求是"筛选条件"而不是"加分项"**：严格控制饮食时直接排除健康度 ≤2 的菜
     （如果只加分，油腻面食能靠"温热顶饱"追平沙拉 —— 这不符合现实）

2. **信号是连续的**，不是 0/1。因为"吃了有多满足"是一个程度问题。

3. **只有被选中的菜能被观测**（bandit feedback）—— 这正是决策数据与普通分类数据的
   根本区别。同一情境下其他 46 道菜的真实效用，模型在训练时是看不到的。

4. **故意制造 12% 的"随手选"**：真人并不总选最优，这部分是不可学习的噪声，
   它决定了 top-1 精确命中率的天花板。

5. **按情境切分，且留出雪天做测试**：同一情境的多次采样不跨集合（避免泄漏）；
   测试集专门包含训练中从未出现的雪天情境，用来检验模型是学到了规则还是死记硬背。

## 4. 模型结构：为什么是两层

```
情境特征 ──►┌─────────────────┐
            │  第一层 CuisineNet │──► 8 个品类的偏好分布（softmax）
            └─────────────────┘
                     │ 选出候选品类
                     ▼
情境 + 菜品 ──►┌─────────────────┐
              │ 第二层 DishScorer │──► 候选品类内每道菜的效用分
              └─────────────────┘
                     │
                     ▼
              在候选品类内取 top-3
```

**用两层的实测理由**（不是理论偏好）：打分器只在「同品类内」训练过排序，
它的分数**没有跨品类可比性**。直接让它对 47 道菜全局排序，效果显著更差。
拆成"先选对大类、再在 6 道里挑"，两类误差不互相干扰。

模型本身是**纯 numpy 手写**的（`train.py`），包含：
- 类别 embedding（`ContextEncoder`）
- 菜品 ID embedding + 菜品属性 embedding
- MLP + 手写前向/反向传播
- Adam 优化器

参数量约 1.5 万，在小数据上不易过拟合，且每一步梯度来源都能看清。

## 5. 训练信号：用了什么、为什么

```python
# 总损失 = 列表内排序损失（只在 chosen 行） + 少量回归损失（全部观测行）
L = softmax_ce(候选品类内 6 道菜的分数, 目标=组内已观测的最高效用)   # 学会"选哪个"
  + 0.3 * huber(该行菜品的预测分, 观测到的效用)                      # 学会"有多好"
```

- **排序损失（主）**：决策的本质是排序，不是拟合数值。
  在候选品类内做 listwise softmax，直接优化"把最该吃的排到第一"。
- **回归损失（辅，权重 0.3）**：保留效用的幅度信息，让分数可用于跨情境比较。
  Huber 而非 MSE，因为效用分布有重尾。

**五个必须知道的坑（本项目都踩过并修复）**：

1. **Huber 必须写成"二次段 + 线性段"两段式**。
   只写 `abs(clip(diff, -δ, δ))` 在 `|残差|>δ` 时是常数函数、梯度为 0，
   与其导数 `clip(diff)` 自相矛盾 —— 梯度检验会以 24% 的相对误差抓出来。
2. **广播维度的梯度必须正确求和，而且"前向广播几次、反向就累计几次"**。
   情境对 K 个候选菜品是同一个，`ContextEncoder` 的 embedding 梯度必须累计 K 次贡献。
   早期实现反过来在反向里除以 K，把情境 embedding 的梯度缩小了 K 倍（317 倍）——
   梯度检验看起来"通过"是因为检验的是同一个错误实现的两侧，
   直到前向改成只编码一次，才由梯度检验确认正确写法是**求和**。
3. **加入"考虑集评分"后必须重新平衡梯度**。回归项从"每 3 行 1 行有效"变成
   "每行都有效"，梯度按行数放大会直接发散（实测回归损失从 0.29 爆到 52201）。
   做法是按情境成组采样，并让回归梯度按该批的观测行数归一。
4. **排序目标必须逐菜不同 —— 这是最隐蔽的一个坑。**
   旧 `group_targets` 写成 `tgt[同品类全部菜] = 该行观测到的单个效用`，
   等于把**一个值广播给品类内每一道菜**。于是 `gt.argmax(1)` 永远返回
   品类内 `dish_id` 最小的那道菜，模型学到的是"每个品类固定答同一道菜"：
   训练损失能压到 0.003，而品类内 top-1 只有 4.83%（≈ 随机 1/17.6）。
   这个缺陷在 47 道菜 / 每类 6 道时被掩盖（1/6≈17%，看着"还行"），
   扩张到 317 道 / 每类 17.6 道后彻底暴露，**平均效用一度低于"永远推荐热门菜"基线**。
   修法是把 `scenario_utility.npy` 的真实效用向量当目标，并用
   **软目标交叉熵**（`softmax_ce_soft`）—— 若对它取 `argmax` 就又退化成"每类一道菜"。
   修复后测试集平均效用 0.5065 → **0.6493**，top-1 1.94% → **51.13%**。
5. **`utility_vector` 的缓存键必须包含所有影响效用的情境列**。
   `taboo` 在效用函数里是"一票否决"，两个只差 `taboo` 的情境（无忌口 vs 素食/海鲜过敏）
   效用向量完全不同。它目前在 `CTX_CAT_COLS` 里所以没出问题，
   但加新情境列时容易漏 —— 评估阶段几千行会静默复用错误向量。

### 一个性能坑：情境被广播到 K 个候选菜品

同一行的 K 个候选菜品共享**完全相同**的情境，但早期 `DishScorer.forward` 把数值特征
铺成 `[B, K, n_num]` 交给 `ContextEncoder`，让 encoder 在 K 个位置上各算一遍。
结果一样，但前向要物化 `[B, K, 63]` 张量、反向要在 `[B, K, ·]` 上做 einsum：

```
单个 batch (B=64 情境 -> 236 行, K=317 道菜 = 74,812 个(情境,菜品)对)
  DishScorer.forward      137.5 ms
  DishScorer.backward    1321.2 ms      <-- 其中 enc.backward 占 1265ms (93.6%)
```

改成**情境只编码一次**（`z2 = enc.forward(cat_idx, num)` 再 `broadcast_to` 到 K），
反向就只需在 `[B, d]` 上做：

| | 优化前 | 优化后 |
|---|---|---|
| DishScorer.forward | 137.5 ms | 58.6 ms |
| DishScorer.backward | 1321.2 ms | 94.1 ms |
| 每 batch 合计 | 1465 ms | **157 ms（9.3×）** |
| 第二层全训练 | 32.2 分钟 | **3.5 分钟** |
| `train.py` 总用时 | 2349.6 s | **282.4 s（8.3×）** |

优化后指标完全一致（无损重构），梯度检验仍通过。

### 梯度检验（`train.py` 启动即跑）

手写反向传播最容易静默出错，所以每次训练前自动做**方向导数检验**：

```
梯度检验（方向导数法：沿随机方向比较解析/数值导数，对 ReLU 折点稳健）
  OK CuisineNet W                 解析=+0.016259  数值=+0.016259  相对误差=9.64e-10
  OK DishScorer enc.W1            解析=-0.001341  数值=-0.001341  相对误差=2.73e-08
  ...
  梯度检验结论：通过
```

> 用**方向导数**而不是逐坐标扰动：ReLU 是折点函数，单点扰动极易落在折点上，
> 数值导数会失真（实测会出现 0.98 的假误差）。

## 6. 怎么评估一个决策模型

决策模型**不能只看准确率**。本项目报四类指标：

| 指标 | 含义 | 为什么重要 |
|---|---|---|
| **平均效用** | 推荐菜品在当时情境下的真实享受程度 | 决策的最终价值 |
| **后悔值** | 最优效用 − 推荐效用 | 距离"上帝视角"差多少 |
| **品类命中率** | 第一层选对大类没 | 定位误差来自哪一层 |
| **top-3 命中率** | 最优菜是否进了前三 | 用户实际会从推荐里挑，前三命中比 top-1 更贴近体验 |

并且必须**和基线比**：随机选、全库最热门、按时段选热门。
如果模型打不过"按时段选热门菜"，那它就没有存在价值。

### 实测结果（测试集，`artifacts/report.md`）

| 策略 | 平均效用 | 相对理论最优 |
|---|---|---|
| 理论最优（上帝视角） | 0.6709 | 100.0% |
| **本模型（两层）** | **0.6581** | **98.1%** |
| 按时段选最热门菜（强基线） | 0.6179 | 92.1% |
| 永远选全库最热门菜（卤水豆腐） | 0.6001 | 89.4% |
| 单层模型（不做品类过滤） | 0.5666 | 84.4% |
| 随机选 | 0.4003 | 59.7% |

| 指标 | 两层模型 | 单层模型 |
|---|---|---|
| 品类命中率 | **70.23%**（盲目按时段猜最热门只有 23.3%） | — |
| top-1 命中全库最优 | **41.12%** | 7.57% |
| top-3 命中全库最优 | **51.97%** | 23.68% |
| 平均后悔值 | **0.0128** | 0.1043 |

**四个值得注意的结论：**

1. **top-1 从 12.62% 提到 50.81%，靠的是修排序目标而不是加容量。**
   47 道菜时品类内只有 6 道，模型直接拟合观测值就能蒙对 1/6；扩到 18 品类 /
   317 道后品类内平均 17.6 道，退化目标立刻现形（top-1 1.94%、效用低于热门菜基线）。
   修好 `group_targets` + 软目标交叉熵后：效用 0.5065 → 0.6493，后悔值 0.1659 → 0.0231。
   期间试过把 embedding 上限从 12 提到 24/36/48，**四组指标一个都没动**（完全相同）——
   瓶颈从来不是容量，是目标函数。（那次实验本身也是无效的，`importlib.reload`
   没真正生效，见 `_exp_capacity.py`；结论后来由"目标退化"这一根因独立解释。）

2. **品类命中率降到 70.2%，但后悔值同时降到 0.0231。** 品类确实选错约 30%，
   可替代品类里也有效用相当的菜，所以效用损失几乎全部来自品类内选菜。
   这也说明"品类命中率"本身不是决策质量的指标。

3. **两层结构仍然必要。** 单层模型（不做品类过滤、直接在 317 道菜上排序）
   效用 0.6055、top-1 23.95%，明显差于两层的 0.6493 / 50.81%。
   打分器只在"同品类内"训练过排序，分数没有跨品类可比性 —— 这一点在 317 道菜上
   比 47 道菜时更明显。

4. **用「考虑集评分」是信息量最大的一条工程经验。** 纯 bandit 数据每个情境只观测
   1 道菜，模型永远不知道同品类其他菜的真实效用，"品类内选哪道"几乎学不动。
   加入 35% 情境的"考虑过的几道菜"评分后（现实中就是收藏/点评/心里记一笔），
   品类内排序立刻变好。在单步决策里，增加"被考虑过的候选"的评分，
   比增加"被选中"的样本更有效。

运行 `python evaluate.py` 生成完整报告（`artifacts/report.md`），
`python inspect_model.py` 做后悔值归因。

## 7. 换成你自己的数据

这个项目最大的价值是**管线**：把 `build_dataset.py` 生成的
`artifacts/samples.csv` 换成你自己的记录即可，其余全部复用。

你的 CSV 只要包含这些列（列名需与 `features.py` 的 `CTX_CAT_COLS`/`CTX_NUM_COLS` 一致）：

```
情境列: time_slot, hunger, available_time, budget, mood, weather,
        companion, health_goal, spicy_tol, taboo
动作列: dish_name, category
信号列: observed_signal      <-- 你自己定义的"结果好不好"，连续值最好
划分列: split                <-- train / val / test，且要按情境切分
```

然后：

```bash
python train.py        # 直接训练
python evaluate.py     # 评估
```

注意三点：
1. `features.py` 里的 `CTX_VOCAB` 需要按你的实际取值改（类别词表）。
2. 你的"菜品"如果不是菜，把 `dishes.csv` 换成你的动作属性表即可。
3. 真实数据一般远不如这里干净 —— 会有缺失、会有选择偏差。
   个人用途可以直接训；一旦用于线上自动决策，就要回到 IPS/DR 那套去偏方法。

## 8. 已知局限

1. **效用函数是我手工设定的常识规则**，不代表你的真实口味。
   比如"减脂期也想吃炸酱面"这种偏好无法体现。接入真实记录后才会被真实信号替代。
2. **品类内菜品高度相似**（最优与次优平均只差约 0.03），所以 top-1 精确命中率天然偏低，
   应看效用和后悔值。
3. **没有做选择偏差校正**。这里的数据是"真人随机选"生成的，不存在系统性偏差；
   真实日志（比如你总是记录自己吃过的，而吃过的受限于附近餐馆）会有偏差，
   那时需要 IPS/DR。
4. **动作空间是 47 道菜**。若扩到几千道，第二层应改为双塔 + 向量检索。
