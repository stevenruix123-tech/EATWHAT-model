# EATWHAT-model

「今天该吃什么」——一个用**两层决策模型**做的用餐推荐器，带本地网页界面。

数据覆盖**长三角（沪苏浙）、珠三角（广府，含港澳）、湖南（湘菜）、东北、四川（川菜）**
五大区域的日常菜品，回答「在什么情况下该吃什么」这个单步决策问题。

- **824 道菜 / 19 个品类 / 20,000 个情境 / 74,242 条样本**
- 模型是**纯手写 numpy** 实现（含手写反向传播与梯度检验），**推理不需要 PyTorch**
- 参数量 **21,526**（float32 不到 90 KB）
- 纯本地运行，**不联网、不调用任何大模型**；服务只绑 `127.0.0.1:8848`

> 📌 2026-11-05：情境数从 2,000 放大到 20,000，同时修正了 `healthy` 标注口径。
> 结果 top-1 从 41% 提到 **53%**、后悔值从 0.0128 降到 **0.0062**。
> 详见 [`docs/交接文档.md`](docs/交接文档.md) §7.1 / §7.2。

## 模型效果（测试集 1,400 个情境）

| 策略 | 平均效用 | 相对理论最优 |
|---|---|---|
| 理论最优（上帝视角） | 0.7114 | 100.0% |
| **本模型（单阶段·整目录 softmax）** | **0.7044** | **99.0%** |
| 按时段选最热门菜（强基线） | 0.6344 | 89.2% |
| 永远选全库最热门菜（卤水豆腐） | 0.6153 | 86.5% |
| 随机选 | 0.4129 | 58.0% |

| 指标 | 数值 |
|---|---|
| top-1 命中全库最优 | 53.29% |
| top-3 命中全库最优 | **78.93%** |
| 平均后悔值 | **0.0071** |
| 品类命中率 | 69.64%（不再是优化目标，仅供参考）|

完整报告见 [`app/artifacts/report.md`](app/artifacts/report.md)。

> ⚠️ **这份测试集 86% 是雪天情境**（故意留出来测分布偏移的），
> 所以绝对数值不能和「常规情境」下的读数直接比。
> 在 2,000 个常规情境的留出集上（5 seed 配对）单阶段是：
> 效用 0.6382 vs 两层 0.6360、top-3 88.27% vs 80.26%、后悔值 0.0004 vs 0.0026。
> 雪天情境上两者效用基本持平（0.7165 vs 0.7178），但单阶段 top-3 更高
> （77.25% vs 68.33%）—— 两层的第一层品类先验在没见过的天气下是个不错的正则，
> 只在效用上占回 0.0013，代价是 top-3 少 9 个百分点。

### 跨规模对比时必须注意（重要）

菜品从 317 道扩到 824 道后，**绝对效用不能直接比**：候选变多，
「总能挑到一道还行的」变容易了，**所有基线都被抬高**，分数区间被压缩
（随机基线 0.4025 → 0.4003 基本不变，但热门菜基线 0.5337 → 0.6001、
按时段热门 0.5572 → 0.6179 都明显上升）。

| | 317 道 / 18 品类 | 824 道 / 19 品类 |
|---|---|---|
| 对理论最优的达成率 | 96.6% | **98.1%** |
| 模型后悔值 | 0.0231 | **0.0128** |
| 最强基线后悔值 | 0.1152 | 0.0530 |
| 模型比最强基线多挽回的剩余差距 | 79.9% | **75.8%** |
| 比热门菜基线高 | +21.7% | +9.7% |
| 噪声上限下 top-1 达成率 | 95.9% | 91.0% |

**结论**：模型相对最强基线的优势基本保持（75.8% vs 79.9%），
后悔值改善 44.6%，但对理论最优的达成率已到 98.1% ——
**继续堆菜品数量的边际收益在递减**，剩下的差距主要是数据里的 12% 噪声。

### 情境数从 2,000 放到 20,000（2026-11-05）

菜品数不变、只放大**情境数**，收益完全不是一回事 —— 这是本项目目前最大的一次提升：

| | 2,000 情境 | **20,000 情境** |
|---|---|---|
| 平均效用 | 0.6217 | **0.6360** |
| 后悔值 | 0.0169 | **0.0026** |
| top-1 | 44.20% | **66.83%** |
| 品类命中 | 67.99% | **85.45%** |
| 训练用时/seed | 56 s | 976 s |

（这组数字是 5 个 seed 配对、在同一套 2,000 情境留出集上测的，全部 5/5 seed 占优、
p<0.001。**别和上表直接比** —— 上表的测试集和这一行的不是同一套。）

原因：`dish_id_emb`（824×8）是模型唯一的「单菜记忆通道」，2,000 情境下
每道菜平均只有约 6 次观测，估不准；2 万情境下每道菜约 60 次，**菜级质量才第一次被学出来**。

## 模型结构：为什么是单阶段（整目录 softmax）

```
情境特征 ──► ContextEncoder(96→24) ─┐
                                    ├─► 全部 824 道菜各打一个分 ──► 全局 top-3
菜品特征 ────────────────────────────┘   （整目录 824 路 soft-CE 训练）
```

**曾经是两层**：第一层 CuisineNet 选品类，第二层 DishScorer 只在选中品类内排序。
这么做的原因是打分器只在「同品类内」训练过，分数跨品类不可比 —— 直接全局排序
会让平均效用从 0.7053 掉到 0.6794、top-1 从 53.07% 掉到 24.86%。

**但两层带来一个改不掉的结构缺陷**：第二层只能在品类内挑。品类一旦选错，
或者是个薄品类（`面包甜点` 只有 9 道菜，硬筛选后剩 3 道），
第 2/3 名就只能是矮子里拔将军 —— 哪怕别的品类里有 20 道更好的菜。

**解法是换训练目标，不是换模型**：把损失从「品类内 masked soft-CE」换成
**整目录 824 路 soft-CE**（目标仍是每道菜各自的真实效用，温度可学习）。
分数因此天生跨品类可比，第二层不需要了。5 seed 配对实测：

| 指标 | 两层 | **单阶段** | 结论 |
|---|---|---|---|
| 平均效用 | 0.6360 | **0.6382** | 5/5 seed，p<0.001 |
| 后悔值 | 0.0026 | **0.0004** | 5/5 seed，p<0.001 |
| top-3 | 80.26% | **88.27%** | 5/5 seed，p<0.001 |
| top-1 | 66.83% | 67.35% | 不显著 |
| 训练用时 | 976 s | **96 s** | ×10 |
| 参数量 | 21,526 | **15,499** | 少了第一层 |

同时试过**双塔**（点积 + learned temperature）：top-1 64.71%、top-3 86.49%，
**输给 MLP 拼接**——纯点积表达力不够，跨特征交互（情境 × 属性）才是关键。

> 代价：单阶段的「品类命中率」从 85.45% 降到 83.41%。这不是退化 ——
> 它本来就不以「猜对品类」为目标，只要最终推荐的效用更高，品类对不对不重要。

## 数据与重新训练

数据与模型都已生成好，**日常只需要启动**。要复现或改数据：

```bat
cd app
python build_dataset.py    :: 生成数据集（约 1 分钟）
python train.py            :: 训练两层模型（约 5 分钟，含梯度检验）
python evaluate.py         :: 生成评估报告 artifacts/report.md
```

### 换成你自己的数据

把 `app/artifacts/samples.csv` 换成你自己的记录即可，其余全部复用。
需要这些列（列名要与 `features.py` 的 `CTX_CAT_COLS` / `CTX_NUM_COLS` 一致）：

```
情境列: time_slot, hunger, available_time, budget, mood, weather,
        companion, health_goal, spicy_tol, taboo
动作列: dish_name, category
信号列: observed_signal      <-- 你定义的"结果好不好"，连续值最好
划分列: split                <-- train / val / test，且要按情境切分
```

⚠️ `app/artifacts/scenario_utility.npy`（每个情境下所有菜的真实效用）
必须由 `build_dataset.py` 一并重新生成 —— 第二层的排序目标依赖它，
缺失或与菜品库不匹配时 `train.py` 会直接报错而不是静默算错。

## 工程上踩过的坑（都写在代码注释里了）

| 坑 | 症状 | 修复 |
|---|---|---|
| **排序目标广播** | 把「一行观测到的效用」广播给品类内每道菜，模型学会「每品类固定答一道菜」：训练损失能压到 0.003 而 top-1 只有 4.83%（≈随机） | 用 `scenario_utility.npy` 的真实效用向量当目标 + **软目标交叉熵**（取 argmax 会再次退化） |
| **encoder 反向广播** | 情境对 K 个候选菜品相同，却让 encoder 在 `[B,K,·]` 上跑前向/反向，`backward` 占 93.6% 训练时间 | 情境只编码一次再 `broadcast_to`，训练 **8.3×** 提速（2350s → 282s），指标逐位一致 |
| **`.bat` 编码** | 存成 UTF-8 后 cmd 报 `'.exe' is not recognized` | cmd 按 OEM 代码页（936/GBK）解析 `.bat`，必须 **GBK + CRLF** |
| **`.vbs` 中文丢失** | 静默启动失效：中文全被替换成 `?`，连 `.bat` 文件名也成了 `??.bat` | `.vbs` 保持**纯 ASCII**，用 `ChrW(&H542F) & ChrW(&H52A8)` 拼中文文件名 |
| **快照界面空白** | `snapshot_ui.py` 存成 `file://` 后 `fetch('/api/meta')` 必然失败，左侧表单整块空白 | 把 meta 内容内联进快照 |
| **快照补丁静默失效** | `snapshot_ui.py` 的 `html.replace` 目标串被改写后变成 no-op，快照悄悄退化成空表单，脚本仍打印「成功」 | `app/smoke_ui.py` 用 AST 抽出全部 replace 目标逐条核对，失效即红 |
| **双数据源** | `build_dataset.py` 硬编码了 47 道菜，与 `dishes.csv` 是两份数据 | 改为从 `dishes.csv` 读取，单一数据源 |

### 容量已验证没有提升空间

在 `app/capacity-study/` 里做过隔离扫描（`dish_id_emb` 维度 × 隐层宽度，8 个配置各 60 轮）：
把参数量加到 **2.14 倍**，验证集 top-1 只动 **+3.66%**，而基线逐轮波动 sd 就有 0.88%；
`dish_id_emb` 从 4 维加到 32 维（8 倍）指标几乎不动 ——
说明模型靠的是菜品属性而不是死记每道菜。**瓶颈在数据噪声，不在容量。**
详见 [`docs/容量扫描结论.md`](docs/容量扫描结论.md)。

## 已知局限（如实说明）

1. **效用函数是手工设定的常识规则**，代表不了真实口味，
   比如「减脂期也想吃炸酱面」体现不出来。
2. **`time_cost` / `price` / `heavy` / `healthy` 等属性是人工估算**，
   不是实测营养数据 —— 建模够用，做营养学结论不够。
3. **`healthy` 口径未完全统一**：广式老火汤的扣分点在嘌呤，
   长三角菜更多是油和糖，同一分值的含义并不完全相同。
4. **「珠三角」实质是广府**（广州/佛山顺德/东莞/中山/香港/澳门），
   深圳、珠海本地菜因缺少可靠来源未收录。
5. **价格是一线/新一线城市单人份估价**，不同城市差异可达 ±40%。
6. **验证集 283、测试集 309 个情境**，1% 的准确率差异只对应约 3 个情境，
   分辨率有限。
7. **容量实验只跑了单 seed**，「4% 以内算噪声」是基于逐轮波动的推断，
   不是严格的初始化方差估计。
